## Audit chunk 00 (30 packets)

Ground rules I verified:
- `t_PACKETHEADER` is 6 bytes: `short m_nSize; WORD m_wType; WORD m_wReserved` (src/client/src/Util/PacketHEADER.h, pack(1)). `Net_Prototype.h` is `#pragma pack(push,1)` from line 219 to line 2927. `CItem.h` is pack(1) too.
- `tagBaseITEM` is 6 bytes (u16 header bitfield + u32 body), the same as XML `Item` (Header u16 + Data u32, same bit order). `tagPartITEM` is 4 bytes (24 bits used, unsigned-int unit). `MAX_BODY_PART` is 10. `MAX_PRICE_TYPE` and `MAX_SELL_TYPE` are both 11. `tag_CLAN_ID` is 10 bytes and `tag_MY_CLAN` is 152 bytes (MAX_CLAN_SKILL_SLOT=20 is defined, so `tagClanBIN` is 120 bytes).
- `Packet_GetStringPtr` returns NULL only when offset >= m_nSize. An empty string ("\0") comes back as a non-NULL "".
- IDL strings are NUL-terminated: `CRoseWriter::set_string` writes the chars then a NUL byte (osirose_common-src/src/rosecommon/include/crosewriter.h:59), and `get_string` reads up to the NUL. IDL bitfields are LSB-first (checked in rose-proto `AppraisalReply`: index `>>0 & 0xfff`, result `>>12 & 0xf`), the same as MSVC.
- `tPOINTF` is `typedef CVec2 tPOINTF` (DataTYPE.h:197), and `CVec2` is `{float x, y}` with no virtuals, so 8 bytes.
- **The client's generated C++ headers are stale.** `cmake-build-release-ssl/gen/packets/include/*.h` date from 2026-08-15, while `_deps/osirose_common-src` XML is from 2026-11-15 (packets HEAD 6ca03ad). The diffs below are taken against the XML. Stale headers in this chunk:
  - `srv_clan_command.h` is empty (no choice body).
  - `srv_clan_icon_reply.h` has no `crc`.
  - `srv_bank_list_reply.h` has no `money`.
  - `srv_allied_chat.h` has no `object_id`.
  - `cli_shop_buysell_reply.h` is missing entirely.
  - Regenerate before migrating any of these. The fetched IDL (`_deps/idl-src`, f36b43c, 2026-11-15) is newer than the clan-packets commit (45ea865, 2026-11-15 12:37), so a plain re-run of the build's generation step should produce the choice-selector classes. The gen dir simply has not been rebuilt since August. If it still comes out empty, IDL is pinned to an older version: check packets #22, "pin IDL master".
- `srv_messenger_chat.xml` exists but is **not listed in `src/rosecommon/CMakeLists.txt`**, so neither C++ nor Rust code is generated for it.

## Live bugs (bucket X)

### 1. PAKWC_CHANGE_MAP_REPLY: the client reads 60 bytes, the server sends 42

The client reads `gsv_JOIN_ZONE` (with `__APPLY_04_10_15_TEAMNO`); the server sends `SrvChangeMapReply`.

| off | client gsv_JOIN_ZONE | XML / server |
|---|---|---|
| 6 | m_wServerObjectIndex u16 | objectIndex u16 (matches) |
| 8 | m_nCurHP i16 | hp u16 (matches) |
| 10 | m_nCurMP i16 | mp u16 (matches) |
| 12 | **m_lCurEXP i64 (12-19)** | xp u16 @12, penalizeXp u16 @14, craftRate u16 @16, updateTime u16 @18 |
| 20 | **m_lPenalEXP i64 (20-27)** | worldRate u16 @20, townRate u8 @22, itemRate[0..4] @23-27 |
| 28 | tagVAR_GLOBAL: world_product i16 @28, updateTime **u32** @30, world_rate i16 @34, town_rate u8 @36, itemRate[11] @37-47, flags u32 @48 | itemRate[5..10] @28-33, flags u32 @34, worldTime u16 @38, teamNumber u16 @40; packet ends at 42 |
| 52 | m_dwAccWorldTIME u32 | (past end) |
| 56 | m_iTeamNO i32 | (past end) |

What the client gets wrong:
- EXP is a mix of xp, penalty and craft/update-time fields.
- The penalty EXP, the whole economy block (`SetServerVAR`) and the world time are garbage.
- The team number (@56-59) is whatever is in the `t_PACKET` buffer past byte 42. CNetwork.cpp:112 allocates one buffer and reuses it per Proc loop, so it is probably leftover bytes from an earlier packet; I did not check whether `Peek_Packet` zeroes the rest. Either way `SetTeamInfo` gets garbage. This is what breaks allied chat and PvP team checks.

The XML is wrong; the client struct is right. Evidence:
- `srv_set_exp.xml` has `exp` as int64_t.
- `srv_global_vars.xml` (the same tagVAR_GLOBAL block) has `update_time` as int32_t.
- The client's struct is the original server's 04.10.15 layout, and the Rust server already stores xp/penalty_xp/update_time wider and narrows them with `as u16` (character.rs:112-119).

Fix the XML to: xp int64, penalizeXp int64, then craftRate i16, updateTime i32, worldRate i16, townRate u8, itemRate[11], flags u32 (or reuse the global-vars layout), worldTime u32, teamNumber i32.

### 2. PAKWC_BILLING_MESSAGE: the XML has the _EXT layout under the plain id

The server sends bytes @6: `01 10 02 00 00 00` (the u16 0x1001 then the u32 2). The client reads `m_btTYPE` = byte @6 = 0x01 = `BILLING_MSG_PAY_FU`.

What the client does with it:
- It appends the system chat line "평생무료 사용자입니다" ("lifetime free user") on every zone entry.
- It calls `CGame::SetPayType(1)`. `GetPayType()` then returns PAY_PREMIUM, because 1 & PLAY_FLAG_KOREA_DEFAULT (the BATTLE bit) is non-zero.
- It ignores the remaining 5 bytes.

So the result is benign by coincidence: a stray chat line and premium pay type. If the default ever changed (say to 0x1003), the first byte would be 0x03 = PAY_FAP and the client would print a different message.

The XML is wrong. `0x1001` is `EXT_BILLING_MSG_PAY_KOREA` and `payFlag` matches `gsv_BILLING_MESSAGE_EXT.m_dwPayType`, so the XML describes PAKWC_BILLING_MESSAGE_EXT and is truncated at that (no `m_dwPlayingFlag[4]`, no msg). The client has no PAKWC_BILLING_MESSAGE_EXT case in CNetwork.cpp at all.

Fix: make srv_billing_message.xml `{type u8, [msg string]}`, and have the server send e.g. `type = BILLING_MSG_PAY_FAP/FU` deliberately. Or move this layout to a `PAKWC_BILLING_MESSAGE_EXT` XML and stop sending it until the client handles it.

## Audit chunk 01 — 33 receive handlers vs packet XML

Basis (checked, not assumed):
- `t_PACKETHEADER` (src/client/src/Util/PacketHEADER.h, `#pragma pack(push,1)`) = `short m_nSize; WORD m_wType; WORD m_wReserved;` = 6 bytes. All offsets below are **body offsets** (after those 6 bytes).
- Net_Prototype.h structs are under `#pragma pack(push,1)` (line 219 to 2927). CItem.h and CUserDATA.h are also pack(1).
- `tagBaseITEM` (client/src/Common/CItem.h) = 6 bytes: u16 {type:5,itemNo:10,created:1} + u32 {gem:9,dur:7,life:10,socket:1,appraised:1,grade:4}. This is the same as XML `Item` (Header u16 + Data u32, same bit order).
- `tagPartITEM` = 4 bytes {itemNo:10,gem:9,socket:1,grade:4}, the same as XML `EquippedItem`.
- `tPOINTF` = `CVec2` {float x,y} = 8 bytes.
- `INVENTORY_TOTAL_SIZE` = MAX_EQUIP_IDX 12 + MAX_SHOT_TYPE 3 + 4*30 + MAX_RIDING_PART 5 (with `_GBC`, which adds RIDE_PART_ABIL) = 140. XML `MAX_ITEMS` = 140. `MAX_PRICE_TYPE` = 11 = XML `MAX_SELL_TYPE`.
- `__APPLY_04_10_15_TEAMNO` is on, so `tag_ADD_CHAR::m_iTeamNO` is an int32.
- IDL `std::string` is NUL-terminated on the wire (rose-proto wire.rs), as `Packet_GetStringPtr` expects.

**The generated C++ headers are stale.** `cmake-build-release-ssl/gen/packets` dates from Aug 15. The XML was updated on 2026-11-15 (commit c9ec10b and later). Proof:
- `srv_hotbar_set_icon_reply.h` is missing, although the XML is in CMakeLists.
- The old `srv_craft_enhance_reply.cpp` reads no count byte, because of the old `occurSize` typo.
- `srv_equip_item.h` has no `get_move_speed`.
- `srv_mob_char.h` and `srv_npc_char.h` have no status tail.

Regenerate the headers before migrating. The table below is computed from the current XML.

## Live bugs (bucket X)

None in this chunk. Every packet the Rust server sends through a generated type has an XML layout that matches what the client reads, byte for byte.

The two packets whose XML differs from the client are both handled by hand on the server, and both are documented in `rust/docs/Zone/Packets Off the XML.md`, so they are bucket B:
- **PAKWC_CLEAR_STATUS**: XML always sends hp then mp at body offsets 6 and 8. The client expects 0–2 i16 values, one for each HP or MP bit that went from set to clear, HP first. skills.rs writes the client's form. The XML is the side that is wrong.
- **PAKWC_DAMAGE**: XML always carries the 18-byte drop tail. The client needs it absent on a kill without a drop, otherwise it spawns a phantom ground item. combat.rs::kill writes the 18-byte short form. The XML needs an optional tail selected by packet size.

## Migration risks to carry forward

- **Regenerate first.** The gen dir is stale, which affects hotbar reply (missing), craft enhance reply (count byte), equip item (move_speed), and mob/npc char (status tails).
- **Raw packets passed outside RecvPACKET.** CRAFT_REPLY goes to `CMakeDLG::RecvResult(packet)`, and GLOBAL_VARS is cast to `tagVAR_GLOBAL*`.
- **Size branches to keep or rethink:**
  - DAMAGE: drop tail present only by size.
  - LEVELUP: exact size check.
  - EQUIP_ITEM and EQUIP_ITEM_RIDE: optional run speed checked by size. With the XML it is always present.
- **Not sent by the server, kept for completeness:**
  - GM_COMMAND and INIT_DATA have no XML (C).
  - CHANGE_SKIN, EVENT_ADD, EVENT_STATUS, FAIRY, GLOBAL_FLAGS, GM_COMMAND_CODE and NPC_SHOW have matching XML (A).

## Basis

- Header: `t_PACKETHEADER` (src/client/src/Util/PacketHEADER.h) is 6 bytes: `short m_nSize`, `WORD m_wType`, `WORD m_wReserved`. **All offsets below are body offsets (0 = first byte after the 6-byte header).**
- Packing: Net_Prototype.h has `#pragma pack(push,1)` from line 219 to line 2927. CItem.h, CUserDATA.h and CHotICON.h also use pack(1). The compiler is MSVC x64 (CMakeCache), so bitfields follow MSVC rules: a new storage unit starts when the declared type changes.
  - `tagBaseITEM` is 6 bytes: a ushort unit holding type:5/no:10/created:1, then a uint unit holding gem:9/dur:7/life:10/socket:1/appraised:1/grade:4. XML `Item` (Header u16 + Data u32) matches it bit for bit.
  - `tagPartITEM` is 4 bytes (uint unit, 24 bits used). It matches XML `EquippedItem` (u32: id10/gem9/socket1/grade4).
  - `tPOINTF` is `CVec2` = 2 floats = 8 bytes (Util/CVector.h has no `virtual`).
  - Checked constants: BA_MAX=6 (so `tagBasicAbility` is 12 B), MAX_UNION_COUNT=10, MAX_MAINTAIN_STATUS=40, MAX_BODY_PART=10, MAX_SHOT_TYPE=3, QUEST_PER_PLAYER=10, QUEST_VAR_PER_QUEST=10, QUEST_ITEM_PER_QUEST=6, MAX_WISH_ITEMS=30, MAX_LEARNED_SKILL_CNT=120.
- Active defines that matter here:
  - `_GBC`: MAX_RIDING_PART = 5, and `tagGrowAbility` gets `m_nPatHP` and `m_dwPatCoolTIME`.
  - `__APPLY_04_10_15_TEAMNO`: team number is int32.
  - `_NEWUI` is **not** defined, so MAX_HOT_ICONS = 32.
  - `__APPLY_EXTAND_QUEST_VAR` is **not** defined, so there is no `m_nEtcVAR` and QUEST_SWITCH_CNT = 512.
  - The client includes the `src/client/src/Common/*` copies of CItem.h, CUserDATA.h and DataTYPE.h. Their layout is the same as `src/common`.
- **Generated headers are stale.** `cmake-build-release-ssl/gen/packets/include` dates from 2026-08-15, but the packets checkout (`6ca03ad`, 2026-11-15) has newer XML:

## Audit chunk 03

Conventions: offsets include the 6-byte `t_PACKETHEADER` (`short m_nSize; WORD m_wType; WORD m_wReserved`, `#pragma pack(push,1)` in `src/client/src/Util/PacketHEADER.h`). `Net_Prototype.h` is under `#pragma pack(push,1)` (line 219). `tPOINTF` = `CVec2` (`src/client/src/Util/CVector.h`: `float x, y;` and no virtuals, so 8 bytes). `tagBaseITEM` = 6 bytes (u16 header bitfield + u32 data bitfield), which matches XML `Item` (Header u16 + Data u32). `uniDAMAGE` = 8 bytes (u32 value, u32 action). `tag_DROPITEM` = 18 bytes (x f32, y f32, item 6, server id u16, owner u16). That equals the drop part of `srv_damage.xml`. `_GBC` is active, so `gsv_EFFECT_OF_SKILL` is the flat 15-byte form (u16 obj, u16 spell, u16 skill, u16 INT, u8 bits).

Strings are NUL-terminated on every side: the client generated reader (`CRoseReader::get_string`), the old `Packet_GetStringPtr`, and the server (rose-proto `wire.rs:169`, `impl Wire for BString`, which writes the bytes and then a 0). A generated ctor stops at the first failed read and keeps the defaults, so an optional tail that is missing reads as the default value. The generated class cannot tell whether the tail was present.

**Generator staleness (client build):** `srv_shop_open.xml` and `srv_toggle_move.xml` were changed on 2026-11-15, but `gen/packets` dates from 2026-08-15. As a result:
- `SrvShopOpen` in gen has no `skin` field and reads `name` at offset 8.
- `SrvToggleMove` in gen has the old enum (RUN=2, SIT=8, DRIVE=9). The XML now has SIT=1, WALK=2, RUN=3, DRIVE=4, RIDE_ON=6.

Regenerate before migrating these two. `srv_skill_cast_position.xml` is not listed in `osirose_common-src/src/rosecommon/CMakeLists.txt`, so it has no generated header (rose-proto has no `srv_skill_cast_position.rs` either). `srv_toggle_move_reply.xml` and `srv_set_animation_reply.xml` repeat the same ePacketType, are not built, and are stale duplicates.
